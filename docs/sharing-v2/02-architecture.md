# グループv2：技術設計

状態：設計・実装前の契約。製品要件は[統合仕様](01-specification.md)、実装済みかどうかは[進捗](05-progress.md)を参照する。既存v1を安全のための基点として保持する。

## 1. 並行するプロトコルと移行

- v1グループは既存schema1と`liflow-shared-1`で継続する。v2を有効にするまで予定・完了・通知の意味を変えない。
- v2は業務schema2と専用の共通Scheduler版を持つ。暗号primitive、署名、端末連番、Lamport clock、因果vector、トランザクション、固定envelopeの再送は既存基盤を再利用する。
- schema2用のentityとpayloadを厳格に検証する。未知の種別・フィールドを既存の`policyData`などに隠して送らない。
- クラウドのrootと送信イベントのschemaを一致させる。schema2へ移行後、schema1の新規送信はRulesで拒否する。旧clientはroot・rosterの未対応版を拒否し、更新を要求する。
- 暗号化Snapshotの形式版と業務版は区別する。元の署名付き事実・操作IDを変更せず、必要な旧事実を保持できるようにする。
- 所有者だけが移行を開始できる。家族／同居人・既定値・旧データの扱いをプレビューし、未送信と端末対応を確認する。移行を署名付きの境界として保存し、過去の個人履歴を含めない。
- 本番Rules/schemaの更新、実グループの昇格は別途明示承認が必要。それまではローカル・Emulatorの検査に限定する。

移行は新しい保護SQLite世代へ構築してから参照を切り替える。旧DBと鍵参照をアーカイブに残し、検証前に置換・削除しない。v1の未送信を新世代へ黙って混ぜない。

## 2. 家事と家事回の直交モデル

共有される定義と手順は既存のchoreを再利用する。v2の家事ポリシーは公開範囲ではなく、共有家事についての完了条件・担当ルール・日時権限を保持する。完全個人家事は別DBなので共有payloadに私的な定義を受け付けない。

| モデル | 主な情報 |
| --- | --- |
| GroupPolicy | 家族／同居人、前後変更、委譲機能、管理者固定、代行、表示・通知の既定 |
| ChorePolicy | 単一完了／対象者別完了、担当ルール、基準日・周期・期間幅、ルール版 |
| AssignmentRule | 家事・対象者・適用開始の家事回・変更理由。完了済みを遡及変更しない |
| Claim | 家事回・引き受け者・解除状態。各人の引き受けを別の因果事実として保持 |
| ClaimResolution | 管理者が観測したclaim IDと正式担当。未観測の同時claimを勝手に消さない |
| Permission | 家事・対象ユーザー・日時指定や前倒し等の権限・付与／剥奪 |
| Designation | 対象回／期間、期限・実施日・固定時間、厳守・管理者固定・権限根拠 |
| ChangeRequest / Decision | 元の指定、提案、受付、期限、承認／拒否／代替／本人承諾 |
| CompletionFact | 家事回、完了対象者、本来担当、実施者、登録者、実施日時、記録日時、履行判定と承認状態 |

基準日は「その端末で初めて見た日」から作らない。共通家事回IDはグループ・家事・基準枠に対応し、個人の推奨や手動移動では変えない。各人実施の対象者別状態は共通回IDとユーザーIDで識別する。担当者の表示順に依存させない。

過去のv1完了の実施者は既存本文、登録者は元の署名のauthorを根拠にする。当時の本来担当・記録日時など復元不能な情報は「旧記録では不明」とし、現在の担当で埋めない。

## 3. イベントと受信権限

全ての新操作もoperationId、groupId、author、端末連番、因果vector、Lamport clock、keyVersionを持つ。ローカルDB・操作・Outbox・派生状態は1トランザクションで確定する。書き込み待ちの後と派生保存の前後にも現在のアカウント・世代・参加状態を照合する。

権限の検査はUI・ローカル計画・復号後の受信で共通のドメイン関数を使う。Firestore RulesはUID・端末・所属・schema・配信順を検査するが、暗号本文の家事単位権限を読めるとは説明しない。

- 管理者の根拠はpinで検証したrosterの所有者UID。所有端末の鍵管理権限と業務上の管理者ユーザーを混同しない。
- 指定の対象、担当、明示grant、固定・厳守、期間外ルールを検証する。委譲機能ONだけでは権限なし。
- 取消は指定された事実の登録者または管理者。本人の取消で他人の独立した完了を消さない。
- 因果的に観測していないgrantで自分の権限を作らない。剥奪・所有者変更と同時の指定は候補と理由を残し、確定した権限へ黙って昇格しない。
- 署名・所属・payloadが不正なら安全停止する。既存の「悪意ある承認済みメンバーの不正イベントからの修復」が解決済みとは扱わない。

順序逆転では因果関係が揃うまで保留する。同じevent集合・検証済みroster集合から同じ業務状態を得る。受信時刻順は競合の勝敗に使わない。

## 4. 期間ルールと時刻

日付はグループの同梱tzdbで解釈する。日付のみとUTC instantの開始・終了を持つ範囲をunionで区別する。時間の重なりは半開区間`[start,end)`とし、終了と次の開始が同時なら重複にしない。時刻付き指定で終了を推測しない。

今回の例外、期間限定、無期限、自動推奨の順で評価する。同じ優先度の因果的な新しいルールは、その適用範囲だけ旧ルールを覆う。前後の区間は残す。因果関係のない重複は候補を保持し、「後から受信したから新しい」と扱わない。

周期変更のプレビューでは家事回例外のID対応を照合する。同じ基準枠へ一意に対応する例外だけを引き継ぎ、曖昧・消滅した枠を近い日へ黙って移さない。完了事実に保存済みの予定・実施日時は変更しない。

## 5. 期限付き承認とサーバー時刻

ユーザー確認済み：オフライン操作は送信待ちで保持し、サーバー受付で正式確定する。操作した端末の元の記録時刻はそのまま残す。

- 申請の正式な起点は、Rulesが`request.time`と一致させた不変のサーバー受付時刻。
- 猶予計算は早い方の対象日時とグループの時刻を使う。日付のみは23:59。1時間以内は正式申請にできない。
- 承認・代替案の本人承諾も受付証拠と期限を照合する。届くまで仮状態で、期限後に届けば失効。オフラインの時計だけで予定を確定しない。
- v1契約で捨てていた`createdAt`を、v2では型のある配信receiptとして扱う。authorの申告時刻とは別。
- 期限を有効化する根拠のreceiptを、所有者が自由に変更できるSnapshotの値だけで信用しない。変更不能なクラウドreceiptとの照合を必要とし、ない場合は未確認で確定させない。
- 時刻根拠が必要なreceiptの保持・整理は、通常のイベントの削除と分ける。容量と長期復帰を検査してから本番へ適用する。

v2イベントと同じトランザクションで、同じIDの`receipts`ドキュメントへサーバー時刻・受付連番・受付時の鍵世代・作者・端末・作者証明のdigestを記録する。Rulesでイベントとreceiptの一致、`createdAt == request.time`、作成後の更新・削除禁止を検証する。再送は元の記録を返し、イベントが整理済みならSnapshotを要求して新しい受付時刻を作らない。このRules差分はローカルEmulator用に検査し、承認なく本番へ配備しない。

digestは平文operationだけでなく、暗号化本文中の作者署名を含むfact全体に結び付ける。クラウドに平文候補を照合するだけのdigestを公開しない。取得にはサーバー読み取りを使い、保留中のローカルTimestampやSnapshot中の値を受付証拠にしない。SQLiteでは元の署名・receipt・投影・受信位置を同じトランザクションで照合する。

権限は元の操作時点とサーバー受付時点の署名済みメンバー情報の両方で検査する。所有権を失ってから届いた管理者操作で共通設定を変えない。一方、交代前に受付済みの正当な履歴まで後の所有権で無効にしない。未送信の本人操作は仮状態、受付証拠のない受信操作は未確認として保持する。Snapshotだけでは本人のOutboxを消さず、後から独立したreceiptを取得したときにも冪等に確認できるようにする。

receiptのサーバー保管は現段階ではイベント整理後も保持する。証拠を失わない容量管理・保管期限は残る検査事項であり、v2の本番有効化条件に含める。

日時指定の解除申請も同じ`ChangeRequest / Decision`と受付証拠を用いる。任意の「自動日時」を手動指定として保存せず、署名付きの`cancellation`に観測した元指定IDと解除範囲を持たせる。`selector: null`は元指定の全期間で、範囲指定は実際の開始回へ照合する。解除後に残る共通ルールから期限計算の基準を再構成し、送信者が任意の遠い期限へ置き換えられないよう受信側でも検証する。必要な同意と受付が揃った解除だけを、観測した確認証拠に基づく除外範囲として投影する。別の日時への代替案は手動指定として区別し、同じ日付であっても解除への賛成を日時指定への賛成に流用しない。元指定・担当・地域が変わった回答は再確認を求める。

参考：[Firestore Request.time](https://firebase.google.com/docs/reference/rules/rules.firestore.Request)。

## 6. 共通Schedulerと個人推奨

共通Schedulerの入力は定義、基準、期間・例外、担当・対象、共通履歴、必須依存、グループtimezoneとルール版。Calendar、天気、個人DB、取得時刻を共通の署名・ハッシュへ入れない。

実施可能期間は基準枠から作る。7日以上の実完了で次の枠を動かさない。2〜6日周期の再実施不要は実際の完了日＋周期日数を下限として、共通枠とは別の状態にする。日次はcivil date単位であり24時間の待機を課さない。未完了の過去枠は履歴として導出し、次の枠を作るために偽の実完了イベントを追加しない。

個人推奨は同じ共通枠を受け取り、本人のCalendar・休日・個人家事・負荷を評価する。初期の時刻帯別負荷スコアは作らず、既存の日別評価を再利用できる境界を持たせる。固定共有予定は勝手に動かさない。

本人の個人家事の自動移動は、自動生成・未固定・未完了で、本人が設定した時刻帯と実施可能期間を満たす場合のみ。同日を先に探索し、他の固定時刻との重複を避ける。同居人では本人許可が必要。時刻帯や所要時間が不足する場合に推測して自動確定しない。

## 7. 本人専用Calendar同期の独立設計

### 暗号化・認可境界

グループ用の鍵・roster・DBとは別のaccount scopeを作る。本人のFirebase UIDだけが読書きできるFirestore領域と、その本人が明示承認した端末鍵を使う。同じグループの管理者UIDやグループ鍵に読取・復号権限を与えない。

本人用の256bit鍵を新たにCSPRNGで生成し、SecureStoreへ別namespaceで保存する。既存のAES-GCM・X25519・HKDF・Ed25519実装と厳密なAAD・署名検証を再利用するが、groupIdと異なるaccount scope・鍵・世代を結び付ける。nonce・saltは暗号化時に生成し、再送は保存済みenvelopeを使う。

初回端末の信頼pinを端末内へ固定する。追加端末は同じUIDで認証した上で、既存の本人端末による番号／QRの照合と署名付き承認を要する。クラウドに置かれた公開鍵をログインしたという理由だけで無条件に信用しない。端末解除は本人用鍵を更新する。グループの退出・管理者交代で本人用鍵を渡さない。

### メイン端末とcache

メイン端末・世代・cache連番を署名付きで持つ。古いメインの遅いcacheで新世代を上書きしない。メイン変更が同時なら競合として確認し、時刻で勝者を決めない。メインが裏にあるだけで別端末を自動昇格させない。

保存するのはbusy区間、取得範囲、取得日時、timezone、Calendar認証主体との私的な紐付け、鍵・メイン世代、ルール版。予定内容・OAuthを含めない。件数とbyte上限、ページングを持ち、最新のcacheを更新する。新しいcacheの全ページが確認できるまで旧cacheを壊さず、失敗では未確認へ縮退する。

取得済み範囲内・鮮度内でのみ「競合なし」を返す。取得失敗、範囲不足、認証変更、メイン世代違い、端末時刻異常は未確認。任意の他ユーザー／日時を受け取る公開照会APIは作らない。

独立テストでは、グループ鍵を持つ別UID、クラウド公開鍵の差替え、異なるaccount scope、改ざん、nonce再送、失効端末、メイン変更、旧cache遅延を検査する。安全性確認・本番承認前に実アカウントの区間をアップロードしない。

参考：[FreeBusyの区間と取得内容](https://developers.google.com/workspace/calendar/api/v3/reference/freebusy/query)、[Expo SDK58 SecureStore](https://docs.expo.dev/versions/v58.0.0/sdk/securestore/)。

## 8. 画面・通知・Google連携

共有ビューは共有Snapshotと個人Snapshotの参照を重ねる。各行は保存先・家事回・対象者を持ち、操作を元のrepositoryへ送る。個人のIDを共有Outboxや共有Googleリストへ流さず、同じ表示からの二重操作を防ぐ。

合成したビューを共有の永続化・ハッシュ・通知・Tasksへそのまま渡さない。共有・個人のProviderと通知namespaceを維持し、共有通知は対象者・暫定担当・完了ポリシーで選別する。完了による通知取消と部分失敗再試行の既存処理を使う。

Tasksの対応はユーザー／グループ／共通家事回／完了対象で安定させる。schema1からの旧ID対応は移行プレビューとaliasで扱い、タイトル一致で再登録しない。Tasks由来の完了も同じ受信権限・代行・履行判定を通し、本人以外の独立事実を取り消さない。

## 9. 保存・検査・公開

既存の排他的SQLite transactionと操作キューを使い、移行失敗では元のファイル・世代参照・Outboxを保持する。Snapshotには未解決の日時・claim、申請、必要な元の署名・履歴・因果情報を残す。旧snapshot・遅延応答を新世代へ入れない。

最初は純粋ドメインと実SQLiteの検査を進める。次にEmulatorのRules／暗号転送、UI、物理端末の順で、[必須検査](03-verification-plan.md)と既存契約を照合する。完了条件は件数だけでなく、実行した経路と結果・未実施の区別を記録する。
