### Phase 2a：純粋ドメイン

`src/features/sharing/v2/`へ、グループ既定値と種別変更、家事の直交ポリシー、日時形式、申請期限、期間ルール、私的Calendarの鮮度・範囲判定、本人許可帯内の移動案、権限の因果評価、同時引き受け、対象を指定した取消、完了と履行、短周期抑制、5日表示の純粋関数を追加した。

新規27テストを含め、iOS条件・Android条件とも915/915、失敗0・スキップ0。既存Firestore Emulator20/20、型検査を通過。機能契約は92件で基点の84件を保持。Calendarの時刻定数とID検証は既存APIからも再公開し、同じ基準を別実装へ複製しない。

ここまでのドメインはまだ共有repository・同期・UIへ接続していない。schema1はschema2を受け付けず、実グループはv1のまま。新しい権限が受信経路でも検査済み、またはv2機能が実機で利用可能、という意味のPASSではない。

### Phase 2b：保存・版境界

schema2の厳密な項目検証、元の操作時刻、安定した共通／担当者別ID、署名・暗号文との版照合、SQLite・Outboxの原子的保存、失敗時の連番保持を追加した。v2の過去ポリシーと権限は、当時の因果関係を検証するためSnapshotにも残す。所有者が署名するv2移行準備は、全メンバーと端末を保持し、新しい鍵世代を要求する。逆戻りとschema1への偽装を拒否する。現行v1の同期と投影は、v2を適用する前に停止する。

iOS条件・Android条件とも926/926、失敗0・スキップ0。Firestore Emulatorは既存20/20。lint・型検査を通過。94機能契約で、従来の契約は削除・緩和していない。全体検査で見つかった既存テストの不完全なenvelopeは、実装の検証を弱めず、正しいschema1のfixtureに修正した。

受信時の業務権限、承認のサーバーreceipt、v2用の投影・UI・Schedulerはこの段階では未接続。v2のクラウド書込みを本番で許可するRules変更や既存グループ移行は行っていない。保存基盤の検査を、v2全機能の完成とは扱わない。

### Phase 2c：受信業務権限と専用イベント保存

署名済みメンバー履歴と操作が観測した因果関係から、D5の一般編集権限、日時委譲、同時引き受け・解除・管理者解決、日時変更と本人同意、代替提案、完了・対象取消を検証する。権限のない受信操作は監査用に残し、業務状態から隔離する。隔離された操作で権限を作ったり、無関係の家事の正当な変更まで止めたりしない。新しい専用DBの投影へ接続し、ローカル不正操作はSQLite・Outboxごとロールバックする。署名の偽造やv2履歴を消したSnapshotは受信位置を進めない。

共通枠の基礎とD6の日時展開を権限検証にも使い、同じ担当者の固定時刻重複を検査する。繰り返し対象は基準日からの日数差と現地時刻を保ち、DSTをまたいでも同じUTC時刻を使い回さない。正式担当に選ばれなかった人の引き受けまで固定扱いで解除できなくなる条件を検査中に発見し、本人の解除を許可するよう修正した。

iOS条件・Android条件とも945/945、失敗0・スキップ0。Firestore Emulatorは既存20/20。lint・型検査を通過。98機能契約で以前の契約を保持する。これらは専用DBのコード検査であり、v2の本番・実機E2Eではない。

この段階の投影は、認証済みの業務factと隔離状態の保存まで。サーバー受付による申請の正式確定、受付時の管理者変更の検査、移行、v2の予定画面・通知・本人専用Calendar同期はまだ接続しない。全v2 factをSnapshotへ保持する暫定的な保守策は、過去権限の証明を壊さないコンパクション設計へ進める必要がある。

## 保存・公開の境界

本番Firestoreのschema・Rules変更、既存グループの移行、mainへのマージ、Draft解除、一般公開は実行しない。承認に進む場合も、先にレビュー可能な差分と検査結果を用意する。既存の個人DB・共有DB・鍵を初期化・置換しない。
