# 開発側セキュリティレビュー — 2026-10-30

この記録は開発工程内の攻撃テスト・コードレビューであり、第三者による独立監査、MASVS認証、全脆弱性の不存在の証明ではない。通常利用のデータ、Google/Firebase本番、課金されるAIへ攻撃リクエストを送っていない。

## 範囲と基準

[OWASP MASVS](https://mas.owasp.org/MASVS/)と[MASTG](https://mas.owasp.org/MASTG/)、APIには[ASVS](https://asvs.owasp.org/)を参照し、保存・暗号・認証と権限・通信・入力と資源制限を確認した。今回は該当項目の重点検査であり、全項目の適合判定ではない。

対象は家電API、端末の公式URL検証、v1/v2共有の署名・鍵配布・Snapshot・権限・履歴・Rules、本人Calendarの保存境界。攻撃者は未ログイン、他グループの所有者、一般メンバー、退出済みメンバー、正しい署名鍵を持つ不正な参加者として構成した。

Cloud試験は localhost のFirestore Emulatorと架空のアカウントだけを使用する。追加スイートはループバックの接続先を明示しないと起動せず、`demo-liflow-security-audit`へ隔離する。

## 再現して修正した問題

| APIのメーカー辞書 | `constructor`は継承した関数、`__proto__`はprototypeを返した。未対応メーカーでもAI呼出しへ進み、検索ドメイン制約が配列にならなかった | 自身のプロパティだけを参照し、未対応ならAI呼出し前に拒否。試験はAIをmock化し、呼出し0を確認 |

| HTML説明書のCPU処理 | サイズ上限内の2MBの未閉じscriptの反復で、隔離した子プロセスが5秒以内に終わらなかった | 前方へ進む走査に変更。未閉じscript・comment・タグ開始の計600万文字（各200万文字）を8秒以内に処理する回帰と、通常の日本語・custom要素・self-closing要素の保持を追加 |

HTMLの問題は公式サイトから受け取る内容の処理で再現したもので、APIへHTMLを直接送って処理させる入口があるという意味ではない。メーカー辞書の問題でコード実行や家事データの漏えいが成立したとは判断していない。APIの結果には既に公式出典の照合がある。ジョブ表も従来から件数制限があり、「無制限にメモリが増える」問題ではなく、他の利用者の結果を早く消す可用性の問題だった。

## 暗号・権限・再送の攻撃試験

- 攻撃者の正しい署名を付け直した暗号文256、nonce32、salt32の計320変異を認証付き復号で拒否。古い署名が不一致になるだけの検査とは分け、320回とも復号処理に到達したことを確認。
- Snapshotと鍵配布に各64の再署名済み暗号文変異を投入。グループ・Snapshot・chunk・世代・受取UID・端末の差し替えも拒否。正常な元データの復号は維持。
- 家族／同居人と共通／各自／担当制の6組合せ、一般メンバー2人について、周期・負荷・有効状態・時間目安など14項目の計168更新を署名して送信し、管理者専用変更を拒否。正規の名前・手順編集は適用。
- 偽の権限付与とそれを利用する後続の日時指定を拒否。無関係の正規編集は適用。
- 同時完了、同一イベントの重複、受信順序逆転、対象を指定した取り消しを照合。他の人の完了は残し、同じ入力集合から同じ予定・履歴へ収束。
- Rulesではv1/v2の各々について、別グループの所有者・メンバー・第三者・未ログインによるroot、event、roster、Snapshot、chunk、ack、v2 receiptへのアクセスを拒否。自分のメンバー情報と鍵だけの正常系も併せて確認。
- 参加者による所有者・端末所有権・鍵世代・共有版・受信位置の書換えを拒否。退出直後に全保護パスと未送信の古い書込を拒否。既存の結合検査で除名・鍵更新・実際の暗号化Session・長期復元も再検査。
- APIでは偽造X-Forwarded-For、CORSの類似origin、Content-LengthとTransfer-Encodingの二重指定を検査。CORSは設定済みの完全一致originだけを反映する。CORSを認証の代わりとは評価しない。

## 版と既存データの保護

端末の公式メーカー検証はv2の家電の判定・IDでも使うため、v2のソース契約を`liflow-shared-2-draft-37`へ進めた。公開済みv1は`liflow-shared-1`と元のソース契約を保持する。

旧draft-36の署名済みデータを新しい版として黙って解釈せず、版の不一致を検出する。旧v2検査用SQLiteや鍵、Cloudの検査データを削除・変換していない。開発用の新しい既定検査名だけを`phase6-v37-a1`へ分ける。過去のPhase 6やUIの証拠はdraft-36時点として保持し、draft-37の両実機総合PASSに読み替えない。既定の通常グループ作成はv1のまま。

## 残る可用性の課題と回復案

この節は基点`0fbe8e5`までの発見記録。後続のv2 draft-38で、所有者の確認付き復旧を実装・検査した。[対応と検査範囲](19-owner-confirmed-recovery.md)を参照。v1の同条件と、本番への配備は引き続き未対応として区別する。

**未解決：承認済みの不正な参加者による、正しい外側署名・壊れた暗号文。** 受信ページの復号が失敗し、その後の同期も止まる。再試行でも同じ結果になることを追加試験で再現した。カーソルとackは進まず、不正な内容を適用しない。独立したローカル編集とOutboxは失われない。

現行の管理者による鍵更新・除名も、先に同期してCloudの先頭と一致することを要求する。したがって「除名すれば必ずすぐ回復できる」とは評価できない。正常なネットワーク破損でも同じ拒否が必要なので、署名や復号を無視してカーソルだけ進める変更は採用していない。

公開前の回復設計案は、(1)不変なサーバー位置と作者・外側署名・暗号文hashを照合、(2)元の暗号文と拒否理由を別の隔離記録へ原子的に保存、(3)管理者に影響する変更と因果関係の欠落を提示、(4)管理者の署名付き回復Snapshotと鍵更新を全端末で同じように検証、(5)元の証拠と未送信変更を残して復元する、というもの。未読データの欠落・鍵取り違えを回復と誤認しないこと、隔離を悪用して管理者変更を消せないことが必要である。これは現行プロトコルにないため、このレビューで未検証の自動スキップを実装していない。

APIの受付上限は1プロセス内の制御で、分散した公開サービス全体の不正利用・費用上限を保証しない。一般公開時のgateway制限・監視・利用者検証は別途必要。第三者サービスへ大量要求する検査は行っていない。

## 保存・実機・検査の限界

秘密鍵と認証の保存はKeychain／SecureStoreのdevice-only設定、共有DBはOSバックアップ対象外のアプリ専用領域を使用する。Android実機では`no_backup/LiFlowSharedSQLite`が所有者のみのモード0700であり、通常のADBシェルの読取りがPermission deniedとなった。接続した開発版はDEBUGGABLEで、明示的に承認したMacの`run-as`で検査できる。公開版の防御を証明したものではない。

iOSの通常画面は実タップによるヘルプ往復を確認。Android 10実機ではNative暗号の既知ベクター、2万区間・22分割、改ざん・旧メイン・解除端末の拒否の12項目がPASS、約11秒。iPhoneでも同じ12項目がPASSし、約2.6秒。初回のURL起動はXCTestのaccessibility読込待ちや開発bundleの再読込で停止したが、bundleの取得完了後に画面を直接確認し、実タップで再検査を完了した。失敗した起動試行を成功には数えない。

端末のroot化・jailbreak、紛失状態の鍵抽出、TLS中間者攻撃、ストア用Release成果物の動的解析、自然なOS背景実行は今回未検証。大量のMobSF用イメージや不要なNative再ビルドは容量を圧迫するため追加していない。ソース解析と開発版の検査をRelease侵入試験と混同しない。
