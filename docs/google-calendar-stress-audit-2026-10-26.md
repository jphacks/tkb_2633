## TasksとCalendar、共通処理とOS差分

1,052件の家事予定を大量に送ろうとした問題はGoogle Tasksの共通同期処理に属する。旧処理ならiOSも同じ経路へ入る。現在の新規作成対象14日以内・HTTPバッチ最大100操作という制限も、iOS・Androidに共通で適用される。

Calendarは、端末のカレンダーアプリを読む方式ではない。両OSともGoogle Calendarの`freeBusy`へ`primary`だけを問い合わせ、忙しい時間を日別の分数へ集計し、共通Schedulerへ渡す。181日分の取得は既存の90日以内の通信単位へ分割する。

認証は差がある。インストール済みライブラリの実装とゲートウェイを確認した。

| 項目 | iOS | Android |
|---|---|---|
| セッション復元 | `signIn`の保存済みセッション復元からKeychainの認証を復元 | 保存済みユーザーを参照。自動取得から対話的になり得る`signIn`へ進まない |
| トークン取得 | 復元後に取得 | 追加の同意画面を出さないよう既存のネイティブパッチを適用 |
| Calendar追加同意 | 前景の明示操作から`calendar.freebusy`だけを追加 | 同左 |
| 日付集計・配置・再試行・DB | 共通 | 共通 |

### 集計の独立照合

UTC、東京、カトマンズ、チャタム、ロードハウ、ニューヨーク、ベルリン、カサブランカ、キリスィマスィ、セントジョンズの10タイムゾーンを対象にした。夏時間の開始・終了、30分の時計変更、ラマダンに伴う変更、年越し、うるう年を含む8つの日付条件を使う。

各条件に64種類の区間集合を生成し、重複・包含・順序の逆転・日またぎ・範囲外の切り落としを検査する。期待値は、実際の時刻を1分ずつ進めてローカル日付を付け、区間の和集合を数える別アルゴリズムで作った。実装の午前0時の二分探索や区間マージを期待値作成に流用していない。秒未満の区間は別の境界テストで確認する。

### 大きなPlannerと同時実行

4件の日次固定を含む21家事について、頻度3モード・休日4パターン・忙しさ32パターンを検査する。忙しさ32パターンが互いに異なることも確認する。日次固定は181日それぞれに1回、計724件を維持する。移動可能期間、依存関係、家事ID、天気による移動先も確認する。標準・こまめの生成件数は1,000件を超える。

100件の同時同期要求は、1回のCalendar取得系列と1回のTasks照合へ合流する。181日分のCalendar POSTは3件。Tasksの読み取りには件数に応じたページ取得があり、ページ取得と重複実行を分けて判定する。

## 再現して修正した箇所

| 問題 | 修正 |
|---|---|
| 15万件の応答を`push(...配列)`へ渡すと`Maximum call stack size exceeded` | 引数へ展開せず、区間を順に追加する |
| `quotaExceeded`・`dailyLimitExceeded`の403が永久的なエラー扱い | 利用上限による再試行へ分類し、既存の1時間以上・Retry-Afterの待機を適用 |
| タイムゾーン変更・日付更新・キャッシュ欠損でも24時間以内だと取得しない | 対象期間の全日が現在のタイムゾーンで新鮮かをSQLiteで確認。通常状態で不足分がある場合に再取得 |
| `NO_ACTIVITY`の障害注入で権限要求待ちへ固定される | `IN_PROGRESS`と同様、ネイティブ処理を実行できない一時的な状態として再試行 |
| 不正な日時・逆転区間を受け入れ、後段の集計で永久エラーへ進む | HTTP応答の検証時点で一時的な不正応答として拒否 |
| 不正なエラー構造や異なる応答期間を空き時間として扱える | 応答構造と、返された期間が要求した期間に一致するかを検証 |
| 保存された時刻が不正だと自動取得が戻らない | 不正な成功時刻・試行時刻・再試行時刻から回復する。正常な待機期限と権限エラーは維持 |
| 巨大なRetry-Afterで無効なDateを作り、保存時に例外になる | Dateで表現できる期限だけを採用し、異常値は通常の待機へ戻す |
| 両OSで100件のセッション確認がSDKのconfigureを100回呼ぶ | 初期化中のPromiseへ合流。失敗した初期化は後で再試行可能 |

既存の`quotaExceeded`テストは、以前の`calendar_http_403`という期待を再試行用の分類へ変更した。仕様上の目的を保持し、失敗を隠すためのテスト削除は行っていない。

## 集計の走査量

日数ごとに全マージ区間を走査していた処理を、順序付け済みの区間を消費する処理へ変更した。日をまたぐ区間は次の日へ保持する。ソート後の走査量は区間数と日数の和に比例する。

MacのNode上で10万の非重複区間・181日を3回ずつ測定すると、中央値は約321msから183msへ変わった。端末上の速度を測定した数値ではない。日別の結果は独立照合と10万区間の専用テストで確認する。
