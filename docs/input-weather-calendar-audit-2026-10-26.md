## 修正

| 箇所 | 再現・確認した問題 | 変更 |
| --- | --- | --- |
| 数字と単位 | 本文用の行間と縦paddingを一行入力にも適用し、数字が単位より下に見える | 共通NumberInputFieldへ移行。段落の行間を外し、縦を中央へ。左右同じ幅の単位欄で横位置も固定 |
| 関連ページ | 個別設定、家電解析結果、毎月のゴミの日数が別々の入力style | 3箇所とも同じ部品へ統一。保存処理・検証範囲は維持 |
| 天気とCalendarの併用 | 通常Schedulerはbusyを考慮する一方、天気で再配置するときの候補日選択には渡っていなかった | 晴れ候補でも移動距離に既存のCalendar負荷ペナルティを加える |
| 洗濯の周期順 | 別周期の洗濯が同じ晴れ日に集まり、日別カードで1件にまとめられるケース | 前後の同一家事の予定日を越えず、同じ日に重ねない |
| 完了の判定 | scheduleEntryIdのない旧形式の完了記録が天気の移動対象になる | 通信の要否と候補の判定を共通化し、既存の完了照合も使う |
| 同じ予報の再評価 | 調整済み予定を次の評価の入力にして、表示や調整件数が変わる | 調整前の通常予定を保持。15分の評価cacheと実行中Promiseを共有 |
| 不要な更新 | 日付が変わらなくても別snapshotを作り、出力処理を繰り返す | 同じ内容ならsnapshotの参照を維持し、DB書き込みを省略 |
| 通信失敗 | 画面は通常予定へ戻っても、SQLiteには以前の天気調整日が残るケース | outcomeにかかわらず実際の日付差分を保存し、表示とDBを一致させる |
| 不明な予報 | 全日分の値がnullでも「取得済み」扱いになる | 取得不可の表示と通常予定へ戻す |
| 遅い応答 | 日付・timezone・設定・Calendarやsnapshotの変更後に旧結果が戻る | 通信開始前と保存前に有効性を確認。古い結果を保存しない |
| 完了後の同期 | 家事を完了するたびにCalendarまで強制取得する | Tasksは即時同期。Calendarは通常の取得間隔に従う。手動の「今すぐ同期」は両方更新 |

busyは従来どおり候補日への加点であり、予定がある日を一律禁止する処理ではない。天気の適合・負荷上限・依存順・移動範囲を先に満たす必要がある。部屋干し、初回保留、期限切れ、完了済み、無効・アーカイブ済みの家事は天気で移動しない。

### 天気の実通信と画面

横浜市の公開地点の予報を実際に取得した。7日分のデータを取得でき、同時2要求と直後の再要求でHTTPは合計1回、約1.1秒だった。

小型の専用検証端末で、洗濯を3日周期・期間幅0日に設定。実際の予報では29日が霧雨、28日が曇り・降水確率24%・降水量0mmで、29日の洗濯が28日に移った。

- [ホームの調整表示](screenshots/input-weather-calendar-2026-10-26/weather-home.png)
- [28日へ移動したカレンダーとカード](screenshots/input-weather-calendar-2026-10-26/weather-calendar.png)
- [28日の完了後](screenshots/input-weather-calendar-2026-10-26/weather-future-completed.png)

28日のチェックで28日の点が消え、26日の2件は維持された。取り消すと28日の点と未完了カードが戻った。SQLiteの日付と実施期間も画面と一致した。

検証前・検証後のDBをローカルに保存し、小型検証端末のデータは検証前へ復元した。全行のダンプ比較が一致し、`PRAGMA integrity_check` は `ok`。通常のHousework QA端末のデータは変更していない。

### Google Calendar・Tasksの実通信

既存のGoogle Tasks Dev端末を今回のコードの開発サーバーへ接続し、追加の権限変更をせず実行した。

- [手動同期の成功画面](screenshots/input-weather-calendar-2026-10-26/google-live-sync.png)
- 04:57:19 JSTの同期でCalendar・Tasksとも成功。Calendarには10月26日〜翌4月24日の181日分、busyのある47日分が日別集計として保存された。
- 検証用の29日の家事を完了。04:58:56にTasks同期が成功し、対応するリンクは `completed`、保留状態なし。
- 同じカードを取り消し。04:59:16にTasks同期が成功し、同じリンクは `needsAction`、保留状態なしへ戻った。
- 両操作の後もCalendarの最終試行・最終成功は04:57:19のまま。従来の「完了のたびにCalendarを強制取得」は解消した。

新規のGoogleカレンダー予定を作る操作は行っていない。既存予定をFreeBusyで取得する経路を実通信で確認し、任意のbusy配置と天気を組み合わせるケースは決定的なテストデータで検証した。

## 重複処理と負荷の測定

macOSのNode SQLiteで、組み込み20件・181日分・1,054予定、日別busyデータと取得済みの予報データを使って測定した。

| 測定 | 結果 |
| --- | ---: |
| 通常予定の生成・保存 | 87.54ms |
| 初回の天気評価・差分保存 | 36.09ms |
| 同じ状態で100回更新した中央値 | 0.144ms |
| 同更新の95パーセンタイル | 0.207ms |
| 予報HTTP要求（差し替えたtransportの計数） | 初回1回、反復中0回 |
| 天気最適化の実行 | 初回1回、反復中0回 |
| 反復中のDB書き込み | 0回 |
| 反復中のsnapshot参照 | 同じ1個 |

この時間はNode上の処理時間であり、iOS/Androidのフレーム時間ではない。OSによるバックグラウンド実行時刻、将来の外部API障害、すべての端末での無停止・無不具合を保証する測定ではない。
