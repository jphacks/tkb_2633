### Phase 2e-1：承認された日時ルールと因果関係

承認された申請から、安定したIDを持つ日時ルールを導出する。同等の承認が追加されてもIDを変えず、追加の署名済みイベントを捏造しない。元の申請・回答・独立receiptから各端末が再構築する。後続の変更申請は、承認されたルールIDと日時を参照できる。変更元の明示と完全な承認証拠を観測していない変更は、承認済みルールを黙って置き換えない。後から承認した人が見た別の日時変更を、元の申請者も見たことにしない。

### Phase 4a：共有カード・自動保存と設定履歴の保護

共有カードの引き受け・完了・対象取消と、管理者用の周期・前後の期間幅・有効状態の自動保存を、署名とOutboxを保存する専用repositoryへ接続した。日付入力はグループのタイムゾーンを使い、存在しない現地時刻や終了時刻のない固定指定を拒否する。画面は共通の文字サイズ・数値入力・チェック部品を使用する。通常ルートへのv2有効化はまだ行っていない。

自動保存では各項目が実際に表示された改訂を保持し、異なる項目の変更だけを合流する。入力中に他端末から同じ項目が変わった場合は上書きせず確認を求める。空欄・不正値を再送せず、画面退出・バックグラウンド移行でも有効な変更を保存する。保存後の表示更新や購読者の例外で、保存済み操作を再実行しない。既存の個人用保存キューにも同じ購読者保護と不要な待機タイマーの解除を適用した。

設定履歴は数値の改訂番号だけでなく因果関係で評価する。大きい改訂番号の別枝で、未確認の将来設定を消さない。周期の変更は元の担当factを再発行せず参照し、未解決の担当競合と対象メンバーを維持する。有効化には明示的な適用日を保存し、無効だった期間を日次家事で埋めない。完了時には、その時点の承認済み共通期間と対象者の期間を検証・保存する。後日の指定取消や、当時は知らなかった同時取消でも、実施履歴を書き換えない。

### Phase 4b：担当変更申請と受付確認の因果関係

固定担当の解除・変更を独立した申請として保存し、管理者の承認／拒否を元の申請と結び付けた。申請と回答の独立receiptが揃うまでは元の担当を保つ。期限後に届いたオフライン承認は監査に残し、担当を変更しない。連打を重複申請・回答にせず、本人以外の申請・管理者以外の承認・別の担当を元とする申請を受信側でも拒否する。解除の承認後に、以前の固定した引き受けが再出現する条件も修正した。

同時の同等な承認は、安定したルールIDと代替となる証拠を保持する。申請だけを知っていた別の担当変更が、後から来た承認を黙って消さない。矛盾する同時回答は確認対象として残し、実際の回答を見た管理者が明示的に解決する。日時ルールと担当ルールは、共通の確認証拠の処理を使う。

検査で、未送信の承認操作を知っているだけの完了が、承認のreceiptを後から受け取ると別の担当・指示で再判定される条件を再現した。未公開schema2へ署名対象の`receiptContext`を必須追加し、「操作を観測済み」と「受付確認を取得済み」を区別した。SQLiteの同じトランザクションから採取し、申請と回答の復元・履歴検証へ適用する。v1はこの項目を受け付けず、公開中のv1の版・計算ソース契約は変更しない。実グループのv2移行はまだ行っていない。

各人実施の家事が承認待ちの間に完了していた場合も、新しい担当へ未完了として開き直さない。履歴の期間・指示・本来担当は元の観測時点を維持する。過去回ごとの判定で全履歴を再走査しないよう、対象家事回の完了・取消・承認の索引と上限付きcacheを使用する。

検査：iOS・Androidの各条件で**1095/1095**、失敗0・スキップ0、lint・型検査通過。**128機能契約**で以前の124件を内容も含めて保持する。Firestore Emulatorは**25/25**で、担当申請→承認→別UIDへの暗号化Snapshot復元を既存の実gateway・Rulesの経路に追加した。v2互換性契約は`liflow-shared-2-draft-8`。Nativeの画面・実機E2Eは引き続き未実施である。

### Phase 4c：周期と担当の同時変更・対応付け

周期を変えた端末と、古い周期への担当変更を承認した端末が互いを知らない場合、以前の実装では承認された担当が適用されず、確認事項も出なかった。再現テストを追加し、旧周期への担当を黙って捨てず、管理者による対応付けが必要な状態として保持するよう修正した。後から別の設定項目を変更しただけで、この確認状態を消さない。すでに周期を置き換えたことを知っている端末からの旧申請の承認も拒否する。

申請中の担当を無関係の周期設定で失わず、将来の適用回を対応付けられない変更には確認を要求する。旧周期で今回限りに指定した担当の対象日が、新しい周期に存在しない場合も確認項目として残す。管理者は対象を指定して解除するか、新しい家事回を明示して対応付けられる。元のfact・申請・承認・実作業は削除しない。対応付けと元指定の解除を同一SQLiteトランザクションへ保存し、不正な担当者を含む変更は全体をロールバックする。

画面が表示した担当・競合のIDを操作時に照合するガードも追加した。担当が変わった直後に古いチェックを押しても、意図しない代行完了を記録しない。取り消しは引き続き元の完了イベントを指定する。

検査：iOS・Androidの各条件で**1105/1105**、失敗0・スキップ0。lint・型検査通過。Firestore Emulator**25/25**で、担当の対応付け・取消を含む暗号化Snapshotの復元と各端末の共通Planner一致を確認した。**131機能契約**で以前の128件を内容も含めて保持する。未公開v2は`liflow-shared-2-draft-9`。v1の計算ソース契約は変更していない。

### Phase 4d：Native画面の隔離検査と保存・取消後の予定

開発ビルド専用ルートへ、実際の署名付きSQLite操作を使うホーム・期限超過一覧・設定・履歴を接続した。合成したユーザー／グループと別DBだけを使い、既存アカウント・個人DB・グループ選択・クラウドには接続しない。releaseでは鍵・ID・DBの初期化前に拒否する。実機で確認済みの既存v1グループをv2へ移行したものではない。

設定の戻るボタン・iOSの画面離脱・Androidの戻る操作は、入力が有効で保存に成功するまで離脱を防ぐ。同時の戻る操作を二重実行せず、保存失敗・他端末からの設定競合では入力を保持して再試行できる。保存後の表示更新だけが失敗したときに、同じ設定をもう一度書き込まない。

### Phase 4f：固定日時そのものが持つ承認条件

日時フォームの接続前に、固定日時に追加の管理者ロック・厳守フラグがない場合、担当者による後ろへの移動が直接確定する欠陥を反例で確認した。固定日時という指定の種類から承認条件を判定するよう修正した。管理者による変更と、通常の日付・期限指定の扱いは変えない。

許可されている前倒しの自動承認は残すが、申請の不変receiptを取得するまでは元の日時を維持する。固定日時を日付・期限指定へ変えて時刻の意味を外す場合は、前倒しを理由に承認を省略しない。厳守・前倒し禁止・自動承認OFFは引き続き承認を要求する。元の固定指定を受信済みの担当者が、正当な署名で直接designationを作っても受信業務検証で拒否し、SQLite・Outboxともロールバックすることを確認した。取消の既存制限も維持する。

### Phase 4g：重複する現地時刻と元の指定の保持

入力された現地時刻が夏時間終了で二度存在する場合、以前の変換は一回目へ黙って決めていた。時刻の候補を同梱tzdbから列挙し、必要な場合だけ「1回目／2回目」とUTC差を選択するよう変更した。入力後に日付や時刻を変えたら選択を解除する。存在しない時刻は引き続き拒否する。30分の時差変更・45分のUTC差・秒とミリ秒・端末の異なる地域設定も検査した。

繰り返しルールにも、元の指定の二回目の時刻を、基準となる家事回ですら一回目へ変える欠陥があった。前版の関数を使った反例では06:30Zが05:30Zへ変わることを確認し、基準回は明示した元のinstantを保持するよう修正した。将来の回で時刻が一意に決まらない場合は`ambiguousTime`として確認を求め、欠落時刻を別の時刻へ自動変換しない。実際の実施を記録した場合も、時刻の指定が未確定という状態を別に保持し、二つの署名付きSQLiteで同じ状態へ収束することを確認した。

同じ候補計算を入力と繰り返し処理で共有する。v1のリマインダー用時計は変更せず、未公開v2の版を`liflow-shared-2-draft-13`へ進めた。日時フォームの適用範囲・初期入力値・元の日時ルールを読む基盤も追加したが、日時変更フォーム自体はまだ接続していない。元の正式時刻が存在しない回の申請期限は[D7](04-open-decisions.md)で確認中で、未回答を同意とみなしていない。

### Phase 4i：存在しない元時刻を変更申請で解決する

D7を実装した。署名された繰り返し元から現地時計の全候補を求め、夏時間の欠落と、周期変更・地域変更・無効な時間帯を区別する。本当に元時刻が存在しない場合に限って申請の`original`をnullとし、変更先の日時だけで期限を計算する。元の指定を確認した明示操作から必ず署名付き申請を生成し、サーバー受付と必要な承認までは正式時刻を未確定のまま維持する。通常の申請で元時刻をnullに偽装する操作、欠落時刻に仮の元時刻を入れる操作、直接指定による承認の迂回を受信側で拒否する。管理者による変更でも同居人の本人承認条件を維持する。

### Phase 4p：固定指定の解除申請と必要な本人同意

一般メンバーも日時フォームから解除を申請できる。本人や管理者の同意が必要な場合は既存の日時申請・回答の仕組みへ保存し、端末に保存しただけでは正式予定を消さない。申請一覧で解除の対象・元期間・解除範囲と状態を表示し、承認・拒否・代替日時の提案と承諾を接続した。解除後の自動計算の基準は期限算出の参考として表示し、確定した手動日時とは扱わない。

解除は新しい手動日時とは異なる操作として署名付き申請と派生状態に保持する。同じ日付を示す代替案であっても本人の承諾まで手動指定を作らず、解除承認と代替日時への賛成が競合すれば全端末で競合のまま保持する。元指定の全期間に対する代替案は、後の回から申請しても元の繰り返し範囲を引き継ぐ。開始回・元指定ID・残る指定・地域・担当を受信側でも再照合し、任意の延期基準や実施可能期間の拡張を解除に紛れ込ませない。

期限後に到着したオフライン承認は失効し、回答履歴と元の日時指定を保持する。解除待ちの間に実施した家事は、受付確認後も当時の指示・担当・実施者・登録者を維持する。本人別の解除を別の対象者へ適用しない。解除後の自動予定は必須依存順を守り、それを理由に早すぎる手動代替案まで許可しない。暗号化同期とSnapshot復元でもこれらの派生状態を再構築する。
