# 共有ワークスペースと画面更新の信頼性監査（2026-10-27）

## 対象と進め方

基点は共有開発ブランチの `1c4150c`。既存70機能契約と834テストを維持し、仕様相談中の担当画面・自動分担などの新機能は追加せず、既存動作の競合・失敗時処理・不要な再計算を調査した。

共有の復元・前景監視・単一worker、SQLiteの接続とトランザクション、通知の作業領域、Google連携との分離、予定のキャッシュを重点的に確認した。天気、家電APIの要求・重複排除・キャンセル、Widgetの完了回収、個別設定の自動保存も既存検査と実装を照合した。

問題ごとに修正前に失敗する再現テストを作成し、修正後に成功することを確認した。端末操作を模したテスト、実際のSQLiteを使うトランザクション検査、ローカルFirestoreの実際のSecurity Rules検査、両OSの物理端末での画面検査を区別する。

## 見つかった問題と修正

| 問題 | 発生条件・影響 | 修正 |
| --- | --- | --- |
| 取消済みの画面更新が復活 | 更新を予約した直後、または実行中の次の更新を予約した後に、画面離脱・バックグラウンド移行が起きる。予約が新しいrevisionを使って実行され、古い通知などを再公開し得た | invalidate時に未開始の予約も破棄する。復帰後の新しい更新は通常どおり受け付ける |
| 購読者からの同期的な離脱後も副作用が実行 | Snapshotの公開に反応した購読者が画面を無効にしても、直後に古いWidget・通知・天気処理へ進んだ | 画面への公開後にもrevisionを照合。中断した出力を「公開済み」と記録せず、同じキャッシュでの次回再開を妨げない |
| データを読めないグループの通知が残る | 権限エラーなどでSnapshotが消えた後、グループの画面を離れる。解除処理がSnapshotの有無に依存していた | 解除にはアカウント・グループに対応する通知namespaceだけを使う。個人や別グループの通知には触れない |
| 1グループの失敗が他を停止 | 保護されたDBを開けない、または私的なGoogle状態を読めないグループが先にある。後続グループの同期と前景監視を開始できなかった | グループごとに失敗を分離し、正常なグループを続行する。アプリが裏へ回った場合は、次のグループの読込を始めない。元の保存エラーは後でworkerへ返し、失敗を成功扱いに隠さない |
| 初期化失敗の接続が残る | 共有レジストリや共有DBの初期化に失敗して再試行するたびに、開いたSQLite接続を解放していなかった | 初期化が成立しなかった新しい接続だけを閉じ、失敗したadapterも解除する。正常なレジストリや別グループの接続は維持する |
| 時間枠を使い切っても別処理を開始 | DBを開く時間が同期の持ち時間に含まれず、共有同期が時間枠を使い切ってもGoogle同期などへ進んだ | DBを開いた後に残り時間を計算し直す。期限を過ぎて新たな同期段階を開始しない。実行中の要求やSQLiteを途中で強制終了するものではない |
| 旧参加状態の応答が再参加先へ混入 | 再参加で端末内の保存世代を更新した後、旧ワークスペースの遅いメンバー情報が届く。一部の保存経路だけ世代の照合がなかった | メンバー情報保存とローカル許可判定にも世代の照合を追加。再参加前のDB・送信待ちを新しい参加状態へ合併しない |
| 変更のない予定を再計算 | 同じ署名済みメンバー情報を読み直すだけで別オブジェクトとなり、参照比較でキャッシュが外れた | 署名済み情報のダイジェストで内容を比較。家事・日付・私的設定・メンバー情報の実変更は引き続き無効化し、許可確認も省略しない |
| 待機中・実行中に変わった権限を見落とす | 呼び出し開始時は有効でも、SQLite待ちや読込・書込中にログアウト・除名などが判明する。キャッシュを返したり、古い許可で編集を確定したりできた | 読込後、実際のローカル操作のトランザクション内、派生データ保存の前後でも許可を再確認。途中で無効になった保存は操作・Outbox・派生行をまとめてロールバックする |

権限の確認にネットワーク要求を毎回加えたわけではない。端末が既に把握しているアカウント・参加状態を、実際の処理時点でも確認する。通信断だけを除名と扱わず、通常のオフライン編集を維持する。

共有を承認待ちの端末へ適用する検証済みの受信処理と、利用者によるローカル編集は分けている。承認待ちのSnapshot取り込みを、ローカル編集用のガードで止めない。

## 回帰検査

新規の回帰ケースを追加し、iOS・Androidそれぞれ862/862テスト、lint、型検査、Expo Doctor20/20、ローカルFirestoreの結合検査20件を通過した。機能契約は77件。基点の70件、そのうち共有追加前の44件は削除・緩和していない。

主な追加検査は次のとおり。

- 更新予約前後・実行中・購読者のコールバック内での取消と、その直後の再開。
- Snapshotがない場合も含む、両OSのProvider終了時の通知解除。
- 未開始の画面更新を取り消した後、復帰時にWidgetの永続的な保留操作を回収し、完了を1件だけ保存・確認するケース。
- 共有DBを開けない場合、私的Google状態を読めない場合の他グループへの影響。
- DBを開く時間を含めたworkerの残り時間と、新規段階の開始抑止。
- 初期化失敗後の接続解放と、新しい接続での再試行。
- 再参加後に届く旧世代のメンバー情報の拒否。
- 内容が同じメンバー情報の再利用と、編集・権限変更時の再確認。
- 実SQLiteで前の書込を保留し、待機中に許可を取り消すケース。
- 派生行の保存途中で許可を取り消し、操作・Outboxとともに元へ戻るケース。

## 物理端末と検証の境界

iPhone 12 / iOS26.7.1はXCTest、Sony I4293 / Android10はADBによる画面操作で検査する。端末の初期化・アンインストール・個人データの共有への取り込みは行わない。

iPhoneは共有ホームの表示と、共有→個人→共有の2往復を確認した。最初の2回はXCTestの自動操作許可の初期化でタイムアウトし、ユーザーが端末上の確認を進めた後に成功した。アプリの処理が失敗した検査とは区別する。

Androidはネット接続前にも個人・共有画面を操作でき、接続後に未受信の変更を取り込んだ。今回の開始時点でiPhoneにあった受信位置62の状態へ追いつき、両端末の共有業務状態のハッシュ一致を確認した。共有内容を古いAndroidの状態へ戻す操作はしていない。

Androidも共有→個人→共有を2往復確認した。検査前後で両端末の個人DBの12テーブル（通知などの個人設定も含む）の全行が一致し、SQLiteの整合性もokだった。両端末は受信位置62・未送信0・同期エラーなしで一致した。

Androidの開発用Toolsボタンが設定ボタンを覆う場合と、画面本体の読込前にテストが判定する場合があった。検査側で既存の設定ディープリンクと読込待ちを使い、製品コードを開発用の重なりに合わせて変更しない。

初期化失敗・権限切り替えの瞬間などは制御した自動検査で再現し、実端末のDBを故意に壊す検査は行わない。OSが自然に起動する長時間のBackgroundTask、Apple実サービス認証、外部による独立した暗号監査は今回のPASSへ含めない。

## 残る制限

- 実行中のFirestore要求が期限後に成立する可能性は残る。要求の取消を保証せず、固定の操作ID・暗号文による照合と再送を使う。
- 承認済みメンバーの不正イベントからの修復、閉鎖グループの暗号文の完全な削除、全端末紛失時の復旧UX、Scheduler版のグループ移行は既存の未完了事項として残る。
- npm auditではExpo CLIからnode-forge / zodへ至る依存経路にhighの指摘が6件残る。直接の6つの独立したアプリ脆弱性という意味ではなく、依存元への波及も含む。今回の照合では自動の互換修正が提示されず、SDKと非互換のメジャー強制更新はしていない。共有暗号にnode-forgeを採用したものではない。
- Wi-Fiの保存・削除を行うアプリコードは見つからなかった。Androidのネット接続設定の問題を、共有同期の不具合と同一視しない。入力されたパスワードをコード・記録・テストへ保存しない。端末の設定画面では接続中のネットワークが保存済みの一覧にもあることを確認した。再接続時に繰り返し入力が必要となる原因は未特定で、端末の再起動やネットワーク削除による検査は行っていない。

共有機能は引き続きDraft。今回の修正を、一般公開前の外部監査や今後の仕様決定の代わりにはしない。
