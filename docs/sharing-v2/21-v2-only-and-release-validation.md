# v2への統一とRelease実機検査

2026-10-30。正本は`main`。v1の利用者はいないというユーザーの確認に基づき、長期のv1互換運用は行わない。既存の検査グループの設定・履歴を移すという指定は維持する。

## 実装

- 新規作成はv2のみ。旧フラグを`false`にしてもv1は作成しない。
- v1の通常のPlanner、編集画面、Google連携、通知、初期カタログ作成を通常利用から外す。個人用SQLiteは引き続き個人用のProviderだけで扱う。
- 旧グループは移行画面だけを開く。既に保存された変更の送受信と署名・履歴の検証に必要な旧形式の読み取りを残す。移行中に旧Schedulerを再計算しない。
- 元の定義、周期、負荷、有効状態、休日、地域、ゴミ収集日、家電、実施・取り消しの署名付き履歴を、独立したv2 SQLiteと暗号化Snapshotへ引き継ぐ。元DBと鍵を消さない。
- 家族／同居人と、各家事の引継ぎ内容を確認して切り替える。旧履歴の実施者・記録者を書き換えたり、不明な過去の担当者・記録時刻を補ったりしない。
- 新しい設定の送信には実際のv2受付記録を使う。私的な段階保存をクラウドの受付済み操作として見せない。切替の応答が失われても、同じ署名付き切替と保存済みの段階から再開する。
- 移行後も個人のOAuth、Google Task ID、本人用Calendar、通知設定を共有データへ含めない。旧グループの私的なGoogle接続情報は元DBに保持し、旧同期を自動で再開しない。
- 移行済みの保存先は再起動時にも同じ場所を使う。退出・除名後の再参加では新しい端末世代の保存先を使い、以前の未送信変更と混ぜない。
- 移行前の履歴はv2の履歴画面で読める。過去の家事回を新しい家事回や新しい完了操作に変換しない。

v2の業務ルールとwire versionは`liflow-shared-2-draft-38`のまま。既存のv2グループを別の計算方式へ変更するものではない。

## 検査で修正した問題

- 移行済みAndroidの再起動で、既存の保存先と、再計算した保存先の名前が食い違う場合を修正。保存先の選択と確認を共通化し、既存のpinを優先する。
- 再参加の際、旧移行pinを`undefined`のプロパティとして残すと署名用JSONの検証に失敗するため、そのプロパティ自体を除いて新しい参加申請を保存する。
- 個別設定の最初の世代が未設定でも、後から別の参加世代へ変わったことを検知する。
- グループの個別設定・履歴は名前を指定したv2の管理画面で読み、個人の時間帯設定を不要に要求しない。別グループを表示中でも対象グループを取り違えない。
- 個別設定から履歴を開く動作を、単に戻る動作から対象のv2履歴へ修正。

## 回帰条件

旧形式を編集するテストは、旧Plannerを公開しないことと、実際のv2設定・移行・再参加を検査するテストへ変更した。個人／共有の分離、アカウント変更・権限変更の拒否、別のグループを指定した編集、保存元データの保持は引き続き検査する。削除されたv1作成へのロールバックを受け入れ条件に残さない。

新たに、元の署名付き履歴の保持、切替応答の消失、段階保存からの復旧、日付変更、アカウント変更、元の履歴の欠落拒否、冷起動時の移行証明の検証、既存保存先の保持、再参加時の分離を検査する。実Firestore RulesとSQLiteを組み合わせ、移行後の周期・負荷・履歴と両ユーザーのoperation indexが一致することも確認する。

## Release実機

iPhone 12とSony I4293（Android 10）へ、既存と同じアプリID・署名のReleaseビルドを上書きインストールした。アンインストールやデータ初期化は行わない。Metroを停止し、Androidの開発サーバー転送も外して検査する。開発用の署名で実機に入れるReleaseビルドであり、ストア配布の署名・公開検査とは別である。

本番Firestoreと既存の別々のGoogleアカウントで、通常画面から検査用v1グループをv2へ移し、両端末で同じ家事と設定を表示した。再起動検査で上記の保存先の不一致を発見し、修正後のRelease版で元のグループを開けることを再確認した。

## OSに任せる背景同期

単一worker・最小60分の指定は維持する。設定の「バックグラウンド同期の実行記録」には、workerの開始・終了、Releaseかどうか、個人Tasks／本人用Calendar／共有の各処理結果だけを最大32件保存する。家事内容、アカウント、グループID、鍵、トークンは保存しない。通常の前景同期・手動同期は、このworker実行記録を作らない。途中でプロセスが終わった記録を成功と扱わない。

自然実行の検査では、対象アプリをホーム操作で背景へ移し、他端末の通常画面から変更を送る。対象アプリを開かず、クラウドの受付位置と、その端末の受信確認位置、worker記録を照合する。強制実行API、jobschedulerの強制起動、テスト用の短い周期は使わない。iOSでのアプリスイッチャーからの強制終了は対象としない。

**この段階の長時間検査は未完了として記録し、その後の修正版でAndroid送信・iPhone受信を1件確認した。** [最終の実測結果](22-background-followup-audit.md)を参照。2026-10-30 15:07 JSTからの最初のiPhoneの背景区間は、途中でユーザーがLiFlowを開いたため検査対象から外した。続く15:37 JSTからの区間では、端末の未送信操作と両端末の受付位置を観測したが、自然実行での送信は確認できなかった。従来の開発用強制実行や前景同期の成功を、この検査の成功へ読み替えない。

## データと自動検査の照合結果

iPhoneの移行前後で、個人データの10業務テーブルと13件の完了履歴は一致した。元の共有DBの業務テーブルと署名付き原本192件も保持した。v2には元の操作198件分のID・digest、完了／取り消し全件、採用中の設定と必要な署名付き原本137件を保持した。既存Snapshotの規則により、上書き済みの家事設定42件と初期状態13件は本文を集約するが、元DBには署名付き原本を残す。v2の送信待ちと拒否された操作はどちらも0件だった。

初回のv2統一時には、両OSの自動テスト各2,313件、Firestore結合検査87件、lint・型検査が通過した。357件の機能契約と52件の必須Cloud回帰を維持している。[集計結果](evidence/2026-10-30-v2-only-release-validation.json)に記録した。

最初のiPhoneの背景区間は、ユーザーがLiFlowを開いたため成功判定の対象から外した。その後の前景同期でAndroidの完了を確認し、iPhoneからの取り消しは15:37:04 JSTに端末のOutboxへ保存した。両端末を背景に保って受付位置を観測したが、取り消しが届いたのは16:38:41 JSTの前景同期だった。この区間の終了後、再参加JSON保存と追加の障害対策を含むReleaseを上書きし、再起動・カレンダー・設定を再検査した。最終の区間と確認できた送受信方向は追加検査記録を参照。

その後の[追加動作検査](22-background-followup-audit.md)で、OS workerの失敗の伝達と複数グループの巡回を修正した。最初の自然実行では、Androidでnativeの終了、iPhoneでRelease callbackの開始を確認したが、共有の取り消しは送信されておらず、変更の同期成功とは判定していない。最新の回帰結果と再検査を同記録へ分けて残す。
