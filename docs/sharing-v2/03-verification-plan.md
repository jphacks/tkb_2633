# グループv2：実装順と必須検査

既存84契約を削除・緩和しない。基点の888テスト／OS、Firestore20件とは別に、新仕様の各経路を実行する。以下は検査計画であり、未実施をPASSと記載しない。

| # | 必須ケース | 検査する境界 |
| --- | --- | --- |
| 1 | 4種類の家事の表示・完了・権限 | 直交ポリシー、対象者別ID、個人保存先、UI操作 |
| 2 | 共通期間一致・本人推奨の相違 | 異なるTZ・busy・休日で共通hash一致、個人hash相違 |
| 3 | 同一人物の端末の再収束 | 別端末鍵、メイン世代、オフライン再送と旧cache拒否 |
| 4 | Calendarの内容の非公開 | UID Rules、別鍵、全共有payloadのallowlist、所有者にも拒否 |
| 5 | 鮮度不明は空きではない | 期限切れ・不足範囲・時刻異常・アカウント変更 |
| 6 | 手動指定と負荷上限 | 確認前は保留、確認後のみ超過を許可 |
| 7 | 同一担当の固定時刻重複 | 半開区間境界、複数担当、日付のみ、別担当 |
| 8 | 条件付き個人家事移動 | 家族管理者、本人許可帯、期間内・同日優先、変更理由 |
| 9 | 本人の固定家事を保護 | 家族管理者でも変更なし、未設定帯を推測しない |
| 10 | 前倒しと厳守・期間外 | 設定表の組合せ、他人担当、固定解除・権限委譲 |
| 11 | 承認期限の境界 | 36/24/12/6/1時間の前後1ms、前倒し先、23:59、DST |
| 12 | 遅れたオフライン承認 | 元の記録保持、server receipt前は仮、期限後は失効 |
| 13 | 期間ルールの部分置換 | 内包・端一致・全包含・無期限・離れた範囲・同時競合 |
| 14 | 周期変更と今回例外 | 安定IDの維持、一意な対応、曖昧時は確認 |
| 15 | 過去の完了を保護 | 担当・周期・ルール・所有者変更の前後で元のfact一致 |

| 17 | 7日以上の周期 | 実完了日の違いで共通枠が動かない |
| 18 | 仮想消化 | 次回枠が進んでも実完了件数は増えず、未完了過去回は参照可能 |
| 19 | 途中参加・担当変更・脱退 | 今回／次回、完了済みを保持、脱退後の再割当待ち |
| 20 | 同時引き受け | 全順序・重複・Snapshot後、全員暫定、管理者の明示解決 |
| 21 | 解決前の実完了 | claim競合中も共通回完了、後の解決と取消でも履歴保全 |
| 22 | 代行と管理者承認 | 許可ON/OFF、実施者・登録者・本来担当、承認待ちと取消権限 |
| 23 | 実施と記録の時刻 | 過去入力、未来不正値、時刻zone、再送で元時刻不変 |
| 24 | 超過5日とカレンダー | 0〜6日境界、折りたたみ、過去回の後日完了 |
| 25 | 同時日時変更 | MV候補、片方を暗黙採用しない、管理者解決と対象限定 |
| 26 | 完了・取消・変更の順序 | 因果穴・全順序・重複・Snapshot、同じ集合で同じ状態 |
| 27 | 剥奪・管理者変更・再参加 | authoring epoch、最新認可、未送信保持、旧世代拒否 |

## 段階と小さな完了条件

1. **Phase 0/1**：現行状態・仕様・差分・設計・未決定事項を保存。アプリ動作は変更しない。
2. **Phase 2a**：ポリシー、日時と期間、承認期限、競合判定、完了状態の純粋関数と反例検査。
3. **Phase 2b**：schema2、受信権限、署名・因果処理の再利用、SQLiteとOutbox・Snapshot・非破壊移行。
4. **Phase 3**：共通枠と個人推奨、短周期と過去回、手動ルールと依存の組合せ。
5. **Phase 4**：UI操作と保存先、担当・申請・解決、通知対象と取消、入力・再入防止。
6. **Phase 5**：本人専用鍵・Rules・cacheの独立検査、その後Calendar・Tasksへ接続。
7. **Phase 6**：iOS/Android条件の全件、lint・型・Doctor、Emulator、必要な実機。公開判断を別にする。

UIテストは実TSXと操作handlerを使い、静的な文字列検索だけで機能の存在を認めない。因果・権限の異常は制御した検査、データ保持・Outboxは実SQLite、クラウド境界はEmulatorの実Rules、画面・native差は物理端末で検査する。

実機はテストグループを使い、個人DBの12テーブル・アプリ設定・既存グループを前後で照合する。本番schemaの変更承認がない場合、v2クラウドの検査はEmulatorへ限定する。実サービス未実施を成功と記録しない。OS任せの長時間実行と強制workerの結果も区別する。
